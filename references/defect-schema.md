# 缺陷输入格式（defects JSON）

脚本的输入是一个 JSON 文件，描述「要把哪些缺陷同步进禅道」。

## 顶层

```json
{
  "source_report": "Test_Case/20260101/xxx.HTML",
  "report_url": "<报告的可访问链接>",
  "defects": [ ... ]
}
```

| 字段 | 必填 | 用途 |
|---|---|---|
| `report_url` | 建议 | 写进每条缺陷的「来源报告」，形成报告 ↔ 缺陷双向追溯 |
| `source_report` | 建议 | 本地报告路径，留档用 |
| `defects` | 是 | 缺陷数组 |

## 单条缺陷

```json
{
  "id": "D-DEMO-01",
  "lv": "P0",
  "ep": "EP-01",
  "title": "示例查询接口 GET /api/v1/example/query 恒定返回 5xx",
  "case": "CASE-01 查询接口正向",
  "ev": "连续 8 次、覆盖 5 组入参组合，全部返回 5xx",
  "actual": "所有组合均返回 5xx「服务暂不可用」，无一成功",
  "expect": "按契约返回 code=0 + 结果字段",
  "fx": "阻断主链路，前端无法展示结果",
  "sug": "在服务端处理入口与内部逐段打点定位异常来源"
}
```

| 字段 | 必填 | 落点 |
|---|---|---|
| `id` | 是 | 幂等键，进标题**末尾** `[SRC:<id>]`；重复执行靠它去重 |
| `title` | 是 | 问题描述（**只写现象**）；脚本自动补 `[<Agent缩写>-Px-X]-` 前缀与末尾 `[SRC:]` 幂等键，见 SKILL.md「缺陷标题命名格式」。**性能类不要自己写 `【性能】`**，脚本按 `type` 自动加（已写也不会重复加） |
| `type` | 可选 | 单条缺陷的禅道类型，覆盖 `config.default_type`（`codeerror` / `performance` / `designdefect` …）。**性能问题必须填 `performance`**：标题的 `【性能】` 标签与 `payload['type']` 同源于此，填错会被门禁拒或漏标 |
| `lv` | 是 | P0/P1/P2/P3/P4，映射 severity/pri 1–4 |
| `ev` | **必须** | 复现步骤 + 证据。**没有复现步骤的缺陷不建单**，回去补 |
| `ep` / `case` | 建议 | 关联端点 / 用例编号 |
| `actual` / `expect` | 建议 | 不给 `expect` 时脚本填默认「按契约应返回业务成功或明确错误码」——**建议自己写**，泛化期望等于没写 |
| `fx` | 建议 | 影响面，决定开发排期优先级 |
| `sug` | 建议 | 修复建议，能指到文件/方法最好 |
| `closure` / `conclusion` | 建议 | 结论块**正文**（数组或字符串）：根因定位、交叉验证、修复建议；标题由脚本条件化，见下节 |
| `closure_gate` | 可选 | 闭环三条件的证据声明；**缺省时结论块标题一律「【修复建议】」**，见下节 |

## 哪些字段**不**写在这里

`assignedTo` / `opened_build` / `default_type` / `severity_map` / `pri_map` **都不在 defects JSON 里**。

它们属于「提交策略」而不是「缺陷事实」，由 `auth` + `meta` 检索后与用户**交互确认**，写进
`zentao_sync.config.json`。defects JSON 只描述缺陷本身——`lv` 是等级，映射到 1–4 由 config 决定。

**唯一例外是 `type`**：`default_type` 仍是整批的提交策略，但单条缺陷可以用 `type` 覆盖它。
原因是性能类标题限定要求标题的 `【性能】` 标签与 `payload['type']` 严格同源——
一批里混着功能缺陷与性能缺陷时，只有逐条声明 `type` 才能既标准确又不被门禁拒。
解析优先级：`defects[].type` > `config.default_type` > `codeerror`（`defect_type(d, cfg)`）。

这样同一份缺陷清单可以换产品、换指派人、换构建复用，不必动缺陷数据；
也避免「指派人写死在缺陷文件里，换个人还得逐条改 20 个文件」。

## 等级 → 禅道字段映射

| lv | severity | pri | 含义 |
|---|---|---|---|
| P0 | 1 | 1 | 阻断主链 / 资金错误 / 数据越权 / 安全后门 |
| P1 | 2 | 2 | 核心功能不可用但有替代路径 |
| P2 | 3 | 3 | 展示 / 交互 / 边界 |
| P3/P4 | 4 | 4 | 低频、优化项 |

映射表在 `config.json` 的 `severity_map` / `pri_map`，可改。

## 写缺陷条目的四条硬规矩

1. **`ev` 必须是能照着复现的东西**：接口 + 入参 + 次数 + 实际返回，缺一不可。
   「接口报错」这种写法不算证据。
2. **`expect` 写契约结果，不写「应该正常」**：写明返回什么 code、什么字段、什么状态。
3. **`id` 一旦用过不要改**：它是幂等键，改了会被当成新缺陷重复建单。
4. **证据不许截断、截图不许只写文件名**：`ev` / 报告里的运行时证据要完整给出；
   有「截图」表头就必须在同行内嵌真图。见下节「截图 / 证据必须直接内嵌」。

## 结论块标题：默认「【修复建议】」

> 本节是 `SKILL.md`「禅道写入准则（通用）」总章的一部分；完整条款见该总章，
> 与标题格式准则、回填准则、截图内嵌准则共同构成本技能的禅道写入准则全集，适用所有禅道写入。

`closure` 只提供**正文**，标题由 `scripts/zentao_sync.py` 的 `closure_allowed(d, target_status)` 做**双闸门**判定：
目标单 `status=resolved` **且**「① 回归测试已执行 ② 根因对应已修复 ③ 状态与解决方案已实际变更为已解决」
三条同时成立、三项证据齐全，才输出 `【代码级验证结论 · 闭环】`；**其余一律 `【修复建议】`**。
**新建单恒为 `active`，所以 `apply` / `create` 路径永远写不进闭环标题**——即便把 `closure_gate` 全填 `true` 也一样；
写入前另有 `guard_steps_rules()` 底层门禁（违规直接拒绝写入），`verify_bug()` 回读也会复查。

| `closure_gate` 键 | 含义 |
|---|---|
| `regression_executed` / `regression_evidence` | 回归已执行 + 回归报告/用例编号与结果 |
| `root_cause_fixed` / `fix_evidence` | 根因已修复 + 提交号/版本号 |
| `resolve_bug` / `resolution` / `resolve_verified` | 需变更为已解决 + 解决方案 + **状态变更已回读确认** |

`resolve_verified` 只能在 `resolve` 成功并回读 `status=resolved` 后填 `true`；「打算改状态」不算。
不要手写标题字符串，也不要在报告表头里写「闭环结论」——统一用「交叉验证 / 修复建议」。
字段样例见 SKILL.md「结论块标题产出限制」。

## 截图 / 证据必须直接内嵌

> 完整条款：`SKILL.md`「截图与证据内嵌产出限制」；判定实现 `scripts/shot_rules.py`。
> 适用所有禅道写入。

产出 defects 与配套报告时，遵循以下四条（禁止「详见知识库报告大图」式的跳转指引）：

| 项 | 要求 |
|---|---|
| 报告全文 | 直接内联 `steps`；来源报告只作溯源，措辞 `（内容已完整内联于本单，团队无需跳转知识库查阅）` |
| 运行时证据 | 完整写入；**禁止** `…（完整证据见知识库报告）`、`…（证据已截断，完整内容见知识库全量报告）` |
| 截图行 | `<tr><th>截图证据（已直接内嵌）</th><td>…<img src="data:image/png;base64,…">…</td></tr>`；不允许只有文件名或「参见他处」 |
| 禁止措辞 | `已内嵌于知识库报告` / `不重复嵌入大图` / `完整证据见知识库报告` / `证据已截断` / `详情见知识库报告大图` 等，清单以 `shot_rules.FORBIDDEN_PHRASES` 为准 |

写 `data:image/png;base64,…` 后，禅道会自动把图落成附件并把 `src` 改成 `fileID=N` 或 `{N.png}`；
回读校验时三种形态都算真图。`guard_steps_rules()` 会在写入前拦截不合规 `steps`，`verify_bug()` 回读复查。
已入库历史报告按「版本只增不改」不回溯重发。

## 从报告里抠条目的做法

报告里的缺陷表通常是 `id / lv / title / ev / fx / sug` 五列，直接映射即可；
`actual` 和 `expect` 若报告里没有独立列，从 `ev` 与 `sug` 里各自抽取补上。
不要为了凑字段编造证据——宁可留空让脚本填默认，也不要编造未发生过的事实。
